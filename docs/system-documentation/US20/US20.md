# US20 – Register an SNS user

## 1. Requirements Engineering

### 1.1. User Story Description

As a **Receptionist**, I want to register an SNS user so that the person can subsequently schedule a vaccination appointment.  The
user story belongs to sprint&nbsp;3 and has high priority.

### 1.2. Customer Specifications and Clarifications

### 1.3. Acceptance Criteria

The following acceptance criteria were established for US20:

1. **AC20‑1 – Format compliance:** the phone number and citizen card number must comply with the Portuguese format.
2. **AC20‑2 – Optional sex:** all fields are required except for the sex attribute.
3. **AC20‑3 – Uniqueness:** the phone number, e‑mail address, citizen card number and SNS user number must be unique across all registered users.

### 1.4. Found out Dependencies

Registering an SNS user is a pre‑requisite for the vaccine scheduling functionality (US30).  The current user story does not
depend on other features but relies on the existence of a service/repository infrastructure to store and query SNS users.  In
this sprint only an **in‑memory repository** is implemented; alternative persistence mechanisms can be plugged in through the
abstract factory introduced for repositories.

### 1.5. Input and Output Data

**Input data:**

- **Typed data:** name, date&nbsp;of&nbsp;birth, sex, postal address, phone number, e‑mail address, citizen card number,
  SNS user number.
- **Selected data:** none.

**Output data:**

- A success or error message confirming whether the SNS user was registered.  In case of an error the message explains
  whether it concerns missing fields, format violations or duplicate data.

### 1.7. Other Relevant Remarks

- Only receptionists are allowed to execute this use case.  Administrators register vaccination centres and personnel, whereas
  SNS users schedule appointments in a different user story.
- The system uses an **abstract factory** to obtain repositories.  In this sprint the **MemoryRepositoryFactory** returns
  an in‑memory implementation of the **SNSUserRepository**, but the architecture allows alternative persistence mechanisms to
  be introduced seamlessly.
- All validation and uniqueness checks are performed in the **SNSUserService**.  The repository merely persists data,
  following the separation of concerns recommended for the Service and Repository patterns.

## 3. Design – User Story Realization

### 3.1. Rationale

| **Interaction ID** | **Question – Which class is responsible for…** | **Answer** | **Justification (with patterns)** |
|--------------------|-------------------------------------------------|------------|----------------------------------|
| **Step 1** | presenting the option to register an SNS user? | `MainView` | **Controller**: The main menu centralizes access to system functionalities and routes the receptionist to the SNS user registration use case. |
| | coordinating the user story? | `RegisterSNSUserController` | **Controller**: Acts as an application controller, mediating between the view and the service layer. |
| **Step 2** | requesting the SNS user data (name, date of birth, sex, postal address, phone number, email, citizen card number, SNS user number)? | `RegisterSNSUserView` | **Information Expert (IE)**: The view knows which input fields must be collected for this use case. |
| **Step 3** | typing the requested data? | `Receptionist` | **Creator (Rule 1)**: In the domain model, the receptionist provides the data required to register an SNS user. |
| | building a structured object with the provided data? | `SNSUserDTO` | **Low Coupling**: The DTO encapsulates all input data and prevents the view from depending directly on domain objects. |
| **Step 4** | validating format and uniqueness constraints? | `SNSUserService` | **Information Expert**: The service knows the business rules and validates data formats and uniqueness. |
| | checking existing phone number, email, citizen card number and SNS user number? | `SNSUserRepository` | **IE**: The repository knows all registered SNS users and can verify uniqueness constraints. |
| | encapsulating persistence details (memory/file/db)? | `RepositoryFactory` | **Protected Variations**: The factory hides the concrete repository implementation from the service. |
| | showing all collected data and requesting confirmation? | `RegisterSNSUserView` | **Pure Fabrication / UI**: The view is responsible for user interaction and confirmation. |
| **Step 5** | confirming the SNS user registration data? | `Receptionist` | **Creator (Rule 1)**: In the domain model, the receptionist confirms the SNS user registration. |
| | creating the SNS user domain object? | `SNSUserService` | **Creator / Service**: The service has all required data and business rules to instantiate an `SNSUser`. |
| | persisting the SNS user? | `SNSUserRepository` | **Information Expert**: Responsible for storing SNS user records. |
| **Step 6** | informing the receptionist of the operation success? | `RegisterSNSUserView` | **Information Expert**: The view communicates the outcome of the operation back to the receptionist. |

**Systematization**

From the rationale the following conceptual classes are promoted to software classes:

- `SNSUser`
- `SNSUserService`
- `SNSUserRepository` (interface)
- `RepositoryFactory` (interface)
- `MemoryRepositoryFactory` (concrete factory)
- `SNSUserMemoryRepository` (concrete repository)
- `RegisterSNSUserController`
- `RegisterSNSUserView`
- `SNSUserDTO`

Other software classes identified:

- `App` – exposes the repository factory and SNSUserService.
- `MainView` – integrates the new menu option.
